## Findings

### F-CI: `main` has been red for the whole epic, and nothing has been deployed

- **F1 (blocking for any deployed use).** Every push to `main` in Epic 2 failed CI: 23 runs in a row, most recently `ecf1606`. The `checks` job fails in `.githooks/test.sh` with "commit with trailer (want 0, got 2)" and "main only in message text (want 0, got 2)", 24 passed and 2 failed (run log of the latest `main` run). `deploy` is skipped every time.
  - PR branches pass (`gh pr checks` for #42–#60: `checks=pass`, `traceability=pass`), because the hook test assumes it is not on `main`.
  - So the cloud project has none of Epic 1's or Epic 2's migrations.
  - This is Epic 1 action A1, which never landed.
  - **Disposition:** fix now (B1, B2).
  - **Upstream lesson:** a red `main` was visible after every merge but blocked nothing. A9's "run on main after merge" check was never added (see follow-through).

### F-S: Seams between stories

- **F2 (declared criterion no longer met).** Story 2.3's criterion says the draft card "reopens the last incomplete step (UX-DR7)" (`epics.md:683`). The card links to `setupPath(event.id)` (`src/modules/events/list.ts:46`), which is always step 1 (`src/modules/events/save.ts:4`).
  - Spec 2.3 (line 28) accepted this while only step 1 existed and said "Stories 2.8 and 2.9 extend it". Neither did: 2.8 only reworded the comment (spec 2.8 triage, edge 8), and 2.9 added step 2 without touching it. Spec 2.8 lists it as a residual risk.
  - **Disposition:** fix now (B3).
  - **Upstream lesson:** a hand-off promised in one spec never became a task in the next one. Carry such promises into the next story's Code Map.
- **F3.** `events_create` is defined in 6 migrations: `20261018120000_events.sql`, `…130000_events_create_reuses_blank_draft.sql`, `…150000_events_cancelled_at.sql`, `…170000_roles.sql`, `…230000_events_description_publish.sql` and `20261020090000_guests.sql`.
  - Each story copies the whole body to add one "not blank" condition. Every copy is pinned by `events_drafts.test.sql`.
  - The risk is that a later copy starts from a stale body.
  - **Disposition:** defer (B10).
- **F4.** The wizard order was changed twice. 2.8 sent step 1 to step 3, and 2.9 sent it to step 2. Each story updated every e2e spec that walks the wizard (2.9: six files). The combined order step 1 → 2 → 3 is pinned in `e2e/guests.spec.ts`.
  - **Disposition:** accept.

### F-D: Duplication map

- **F5.** The read-only rule (cancelled, or published and `ends_at < now()`) exists in 4 SQL places: `events_refuse_read_only`, `guests_add`, `guests_update` and `guests_remove`. Each is pinned per function by pgTAP since 2.10.
  - It also exists in 6 TS places as `!isDraft(event) && isPast(event, new Date())`: `settings/page.tsx:30`, `setup/page.tsx:24`, `setup/description/page.tsx:24`, `setup/guests/page.tsx:30`, `team/page.tsx:32` and `guests/page.tsx:27`.
  - **Disposition:** the TS copies are fixed now with one `isReadOnly(event)` in `list.ts` (B4). The SQL copies are accepted while pgTAP pins each one.
- **F6.** The mapping from error code to Result is written five times: `refuseEventChange` (`events/actions.ts:176`), `refuseGuest` (`guests/actions.ts:18`), and inline blocks in `saveQuestionnaire`, `updateSchedule` and `setRoleActive`.
  - **Disposition:** accept. The messages differ per surface on purpose.
- **F7.** `useSaveFeedback` is exported from the route file `app/events/[eventId]/setup/form.tsx:95` and imported across routes by `setup/description/form.tsx:9`, `guests/add-guests-form.tsx:9` and `guests/guest-rows.tsx:12`.
  - Spec 2.8 rejected moving it into `save.ts` because that module is imported by `"use server"` actions. A client-only file in `src/components` avoids that problem.
  - **Disposition:** fix now (B5).

### F-P: Pattern divergence
